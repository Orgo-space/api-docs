Orgo can push event notifications to a URL you control. Subscribe to any subset of 24 event types, register an HTTP(S) endpoint, and Orgo delivers a signed JSON POST every time a matching event happens.

This page is the reference. For a complete walkthrough, including idempotent handling and replay, see [Handle webhooks](/api-reference/recipes/handle-webhooks).

---

## Available events

| Family | Events | When they fire |
|---|---|---|
| **User** | `user.created`, `user.updated`, `user.deleted` | New registrations, profile changes, account deletion |
| **Payment** | `product_payment.created`, `product_payment.updated`, `product_payment.deleted` | Stripe checkout, offline payments marked paid, refunds |
| **Event attendance** | `event_attend.created`, `event_attend.updated`, `event_attend.deleted` | Member RSVPs, confirmations, check-ins, cancellations |
| **Contract** | `contract_user.created`, `contract_user.updated`, `contract_user.deleted` | Contract assigned, signed, force-resign |
| **Role** | `user_role.created`, `user_role.updated`, `user_role.deleted` | Permission grants and revocations |
| **Contact** | `contact.created`, `contact.updated`, `contact.deleted` | CRM contact added, updated, removed |
| **Badge** | `badge_user.created`, `badge_user.updated`, `badge_user.deleted` | A badge is awarded to a member, changes, or is removed |
| **Badge step** | `badge_user_step.created`, `badge_user_step.updated`, `badge_user_step.deleted` | A member's checklist step for a badge is added, checked or changed (for example through `POST /api/v1/badge_users/{id}/steps`) |

Every event ships with the entity snapshot (`object`) and, for updates, a diff (`previous_attributes`). The OpenAPI spec declares a typed payload schema for the first 18 events (the six families above the badge rows). The badge and badge-step events share the same envelope but have no typed schema yet.

## Subscribing

An Orgo administrator creates a subscription in the admin UI under **Settings → Developers → Webhooks**, or with the API:

```bash
curl -X POST https://acme.orgo.space/api/v1/webhook_subscriptions \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CRM sync",
    "url": "https://your-app.example.com/webhooks/orgo",
    "eventTypes": ["user.created", "product_payment.updated"],
    "secret": "whsec_a3f8b2c4d6e8f1a3b5c7d9e1f3a5b7c9",
    "isActive": true,
    "description": "Sync new members and payments into our CRM."
  }'
```

| Field | Notes |
|---|---|
| `name` | Required. A label for you |
| `url` | Required. See [Where deliveries can go](#where-deliveries-can-go) |
| `eventTypes` | Required. Any of the event types above. There is no wildcard |
| `secret` | Optional but strongly advised. Used to sign each delivery. The API never returns it again |
| `isActive` | Defaults to `true`. Set `false` to pause deliveries |
| `maxRetries` | 0 to 10, default 3. The maximum number of delivery attempts, see [Retry behavior](#retry-behavior) |
| `timeoutSeconds` | 1 to 300, default 30. How long Orgo waits for your response |
| `headers` | Extra headers to send with every delivery, for example a bearer token for your gateway |
| `description`, `metadata` | Free text and free-form data for your own bookkeeping |

The `secret` is yours to choose: a 32-byte random string is standard. Orgo uses it to sign each delivery so you can verify the payload came from Orgo. The response includes the subscription `id`, counters (`totalDeliveries`, `successfulDeliveries`, `failedDeliveries`) and `lastTriggeredAt`.

Managing subscriptions (create, list, update, delete, test, read logs) requires an Orgo administrator.

### Where deliveries can go

The URL is checked when you save it and again at every delivery:

- Only `http` and `https`, on the standard ports 80 and 443, and with no credentials in the address.
- The host must resolve to a public address. Private ranges, loopback, link-local and cloud-metadata addresses are refused.
- A redirect is followed only to another address that passes the same checks, and only a few times.

A refused address is rejected with `422` when you save, and a delivery to an address that later stops qualifying is logged as failed and **not retried**.

## Payload envelope

Every delivery, regardless of event type, has the same outer shape (Stripe-inspired). Only the `object` and `previous_attributes` differ per event.

```json
{
  "id": "wh_evt_67aa128c2f4a",
  "event": "user.created",
  "api_version": "2024-01",
  "created": 1735689600,
  "tenant_id": 1,
  "request": {
    "id": "req_8c2f4a67aa12"
  },
  "object": {
    "@id": "/api/v1/users/42",
    "id": 42,
    "firstName": "James",
    "lastName": "Patterson",
    "email": "james.patterson@example.com",
    "status": "NEW"
  },
  "previous_attributes": null,
  "is_update": false,
  "entity_type": "user",
  "operation": "created"
}
```

| Field | Always present | Notes |
|---|---|---|
| `id` | yes | Unique per event: **the idempotency key** |
| `event` | yes | The event type (e.g. `user.created`) |
| `api_version` | yes | Schema version of the payload (currently `2024-01`) |
| `created` | yes | Unix timestamp (seconds) when Orgo emitted the event |
| `tenant_id` | yes | The Orgo tenant ID, for routing in multi-tenant receivers |
| `request` | yes | Metadata about the API request that triggered the event |
| `object` | yes | Snapshot of the entity at the moment of emission |
| `previous_attributes` | only on `*.updated` | Diff against prior state; `null` on create/delete |
| `is_update`, `entity_type`, `operation` | yes | Denormalized helpers |

The OpenAPI spec declares a `Webhook.<EventName>` schema for the first 18 event types (for example `Webhook.UserCreated`). Use these in your typed client for autocomplete and validation.

## Delivery headers

| Header | Purpose |
|---|---|
| `X-Webhook-Event` | The event type (e.g. `user.created`) |
| `X-Webhook-Delivery` | Unique delivery ID. Log this; it appears in the delivery logs |
| `X-Webhook-Timestamp` | Unix timestamp of when this delivery was sent (use it for replay defense) |
| `X-Webhook-Signature` | HMAC-SHA256 over the delivery, keyed with the subscription secret. Sent only when the subscription has a secret (see below) |
| `Content-Type` | `application/json` |
| `User-Agent` | `OrgoWebhook/1.0` |

Headers you configured in `headers` are added to these.

## Authenticating the sender

Set a `secret` on the subscription and every delivery carries `X-Webhook-Signature` in this shape:

```
X-Webhook-Signature: t=1754413200,v1=3f9c0e2b…
```

| Part | Meaning |
|---|---|
| `t` | Unix seconds at signing time. Same value as `X-Webhook-Timestamp` |
| `v1` | `HMAC-SHA256(secret, "<t>." + raw request body)`, hex encoded, lowercase, 64 characters |

The timestamp is inside the signed string, so it cannot be edited without invalidating `v1`. That is what lets you reject a captured delivery replayed later. A subscription with no secret sends no `X-Webhook-Signature` header at all.

Verify against the **raw body**. A body that has been parsed and re-serialized is a different byte string and will not match.

```javascript
const crypto = require("crypto");

function verify(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(
    header.split(",").map((p) => p.split("=", 2))
  );
  if (!parts.t || !parts.v1) return false;

  if (Math.abs(Date.now() / 1000 - Number(parts.t)) > toleranceSeconds) {
    return false; // too old, or too far in the future
  }

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${parts.t}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "utf8");
  const b = Buffer.from(parts.v1, "utf8");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

```python
import hashlib, hmac, time

def verify(raw_body: bytes, header: str, secret: str, tolerance: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if "t" not in parts or "v1" not in parts:
        return False

    if abs(time.time() - int(parts["t"])) > tolerance:
        return False

    expected = hmac.new(
        secret.encode(),
        parts["t"].encode() + b"." + raw_body,
        hashlib.sha256,
    ).hexdigest()

    return hmac.compare_digest(expected, parts["v1"])
```

Respond `401` and log the delivery ID when verification fails. Orgo treats that as a failed delivery and retries it, which is the behavior you want if the failure is your own misconfiguration.

Each retry is signed at the moment it is sent, so the same delivery ID can arrive with different `t` and `v1` values. Deduplicate on the payload `id` or `X-Webhook-Delivery`, never on the signature.

<Warning>
This format shipped in August 2026 and replaced a short non-keyed checksum. There is no compatibility header: a receiver comparing the old value must move to the recipe above.
</Warning>

## Idempotency

Orgo may deliver the same event twice: retries after a slow response, or network races on at-least-once delivery. Your handler must be safe to call repeatedly with the same payload.

The simplest pattern: track processed deliveries by `payload["id"]`.

```python
def handle(payload: dict) -> None:
    delivery_id = payload["id"]
    with db.transaction():
        if db.processed_deliveries.exists(delivery_id):
            return  # already handled
        db.processed_deliveries.insert(delivery_id, processed_at=now())
        dispatch(payload)
```

Keep delivery IDs for at least 30 days. If you can, insert the dedup row in the same transaction as the side effect. That closes a window where a crash mid-handler leaves the dedup row but not the effect.

## Retry behavior

| Trigger | Behavior |
|---|---|
| Receiver returns 2xx | Marked delivered. No retries |
| Receiver returns non-2xx | Retried with exponential backoff while attempts remain |
| Receiver doesn't respond within `timeoutSeconds` (30 by default) | Treated as failed; retried |
| Receiver TLS or connection error | Treated as failed; retried |
| Address not allowed (see above) | Logged as failed; **never retried** |
| Attempts exhausted | Marked failed in the delivery logs |

`maxRetries` is the maximum number of attempts for one delivery. With the default of 3, Orgo calls your endpoint at most three times: the second attempt comes 20 seconds after the first failure and the third 40 seconds after the second. The delay doubles with each attempt (20, 40, 80 seconds, ...) up to 10 minutes. Setting it to `0` or `1` disables retries.

The subscription itself is **not** deactivated on repeated failures. Watch `failedDeliveries` on the subscription, or your own error rate.

## Delivery logs and replay

Every delivery attempt, success or failure, is logged with the request payload, your response status and body, and the time taken. To list the most recent ones:

```bash
curl "https://acme.orgo.space/api/v1/webhook_subscriptions/3/delivery_logs?limit=100" \
  -H "Api-Token: $ORGO_API_TOKEN"
```

`limit` defaults to 100 and is capped at 500. The original payload is stored with each log, so you can replay a failed delivery locally without waiting for Orgo to send it again. Do not rely on the log as a long-term archive: take what you need promptly.

## Testing

Before going live, send a synthetic event to your endpoint:

```bash
curl -X POST https://acme.orgo.space/api/v1/webhook_subscriptions/3/test \
  -H "Api-Token: $ORGO_API_TOKEN"
```

No body is needed. Orgo queues one delivery with the event type `webhook.test` and answers immediately with `{"success": true, "message": "Test webhook dispatched successfully", "delivery_id": "..."}`. The delivery itself is asynchronous, so look at your endpoint or at the delivery logs for the result. The test payload describes the subscription (`name`, `url`, `event_types`, `is_active`) rather than a member, and it carries the same headers and signature your handler sees in production. It is not an example of any real event's `object`.
