Rate limiting on the Orgo API is **per endpoint**, and the key differs by endpoint: some limits count per account, some per IP address, some per email address or per OAuth client. There is no single global bucket, and **most endpoints have no application-layer limit at all**; they are only protected by platform-level throttles. Limits exist where an endpoint sends email, is expensive, or can be used to guess secrets.

---

## How a limit looks

When you hit a limit the API answers `429 Too Many Requests`, normally with a `Retry-After` header in seconds:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 47
```

The body is a framework error (see [Errors](/api-reference/concepts/errors#error-envelopes)) whose `detail` names the cause, for example `Too many ticket holds. Please try again shortly.` Read the status and the header, not the exact text.

Read-heavy endpoints (`GET /api/v1/users`, `GET /api/v1/events`, and so on) are not application-rate-limited under normal circumstances, so you can paginate freely.

## Limits you can hit

| Endpoint or family | Why limited | Limit |
|---|---|---|
| `POST /api/v1/login-check` (password login) | Password guessing | 5 failed attempts per username and per IP within 15 minutes. Successful logins never count |
| `POST /api/v1/request-login-otp` | Email abuse | One code per 20 seconds per address, at most 10 codes in 5 minutes, then a lockout |
| `POST /api/v1/verify-login-otp` | Code guessing | 15 attempts per code, and a 10-minute lockout after 10 failed verifications for one address. A code expires after 5 minutes |
| `POST /api/v1/password-forgot` | Email abuse | 10 per hour per IP, plus a one-minute cooldown per account |
| `POST /api/v1/users/{id}/send-password-reset` | Email abuse | One request per minute per member |
| `POST /api/v1/oauth/register` | Open registration | 10 per hour per IP |
| `POST /api/v1/oauth/token` | Secret guessing | 10 **failed** client authentications per `client_id` within 5 minutes. A correct secret is never throttled |
| `POST /api/v1/events/{uuid}/ticket-holds` | Inventory hoarding | 12 per hour per IP and event |
| `POST /api/v1/public/event/{uuid}/validate-voucher` and `GET .../link/{token}` | Code guessing | 10 per minute per IP and event |
| Starting a permission-impersonation session | Abuse of a powerful action | 5 starts per minute per administrator |
| `GET /api/v1/s3-upload` (anonymous callers) | Storage cost | 20 per hour per address. Signed-in callers are not counted here |
| Identity document uploads by hash | Guessing | 15 per hour per IP |
| `POST /api/v1/users/{id}/send-email`, `POST /api/v1/contacts/{id}/send-email` | Mail reputation | 30 per hour per admin |
| Public forms (`form-submit`, contact requests, newsletter sign-up widgets) | Spam | A handful per hour per IP, for example 10 form submissions or 5 newsletter registrations |
| Email-exists check during registration | Enumeration | 30 per hour per IP |

Newsletter sends go through a managed outbound queue rather than a visible limit: the platform sends at a steady rate, so a large campaign takes minutes to flush, not a `429`.

Where an endpoint's reference page does not mention a limit, assume none beyond platform protections.

## Designing for the limits

<AccordionGroup>

  <Accordion title="Bulk operations: batch instead of looping">
    Many endpoints have explicit bulk variants: `POST /api/v1/contacts/bulk-delete`, `POST /api/v1/waitlist_entries/bulk-approve`, `POST /api/v1/events/{uuid}/attendees-bulk` and others. Each bulk call is **one** request and is far cheaper than N individual calls.
  </Accordion>

  <Accordion title="Pagination: use the maximum page size">
    `itemsPerPage=100` is the cap. A smaller page size means more requests for the same data. Use 100 unless you have a reason not to.
  </Accordion>

  <Accordion title="Polling: switch to webhooks">
    If you find yourself polling `GET /api/v1/product_payments?status=open` every few seconds, subscribe to the `product_payment.updated` webhook instead. See [Webhooks](/api-reference/concepts/webhooks).
  </Accordion>

  <Accordion title="Sessions and OAuth: cache tokens">
    Do not sign in before every request. Keep the session JWT (about 11 days by default) and sign in again only when a request returns `401`. Cache OAuth access tokens and refresh on demand, never on every call. An Api-Token does not expire unless you set an expiry.
  </Accordion>

  <Accordion title="Background sync: go off-peak">
    For nightly syncs, schedule them in your tenant's off-hours. A thousand sequential requests at noon still adds latency on top of normal member traffic.
  </Accordion>

</AccordionGroup>

## Retry pattern

A safe pattern that handles both `429` and transient `5xx`:

```python
import time
import requests

def call(method, url, **kw):
    backoff = 1
    for attempt in range(6):
        r = requests.request(method, url, **kw)
        if r.status_code == 429:
            wait = int(r.headers.get("Retry-After", backoff))
            time.sleep(wait)
        elif r.status_code >= 500:
            time.sleep(backoff)
        else:
            return r
        backoff = min(backoff * 2, 30)
    return r
```

The same pattern in JavaScript or TypeScript:

```ts
async function call(input: RequestInfo, init?: RequestInit): Promise<Response> {
  let backoff = 1000;
  for (let attempt = 0; attempt < 6; attempt++) {
    const r = await fetch(input, init);
    if (r.status === 429) {
      const retryAfter = Number(r.headers.get("Retry-After") ?? backoff / 1000);
      await new Promise(res => setTimeout(res, retryAfter * 1000));
    } else if (r.status >= 500) {
      await new Promise(res => setTimeout(res, backoff));
    } else {
      return r;
    }
    backoff = Math.min(backoff * 2, 30000);
  }
  throw new Error("call failed after 6 attempts");
}
```

## Per-plan limits

There is no per-plan rate limit at the application layer. Higher-volume plans get more generous platform-level concurrency, but the endpoint limits above are the same for every plan. If you need a limit raised for a specific tenant and endpoint, such as a high-volume webhook sender or a large nightly export, contact support.
