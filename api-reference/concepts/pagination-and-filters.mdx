Every collection endpoint in Orgo (`GET /api/v1/users`, `GET /api/v1/events`, `GET /api/v1/product_payments`, ...) supports the same pagination, filtering, and ordering query parameters. Once you learn the pattern on one endpoint, the rest follow the same shape. Which filters a given collection accepts is listed under that endpoint's **Parameters** in the reference.

---

## Pagination basics

| Query parameter | Purpose | Default |
|---|---|---|
| `page` | 1-indexed page number | `1` |
| `itemsPerPage` | Page size, capped at **100** | per resource |

The default page size is set per resource. Most collections use 30, users use 50, and a few reference lists are larger (countries use 1000). The reference shows the default under each endpoint's `itemsPerPage` parameter. Whatever the default, a request that asks for more than 100 with `itemsPerPage` gets at most 100.

```bash
# First page, default size
GET /api/v1/users

# Second page, 50 items per page
GET /api/v1/users?page=2&itemsPerPage=50
```

### `page` must be a positive whole number

A `page` of `0`, a negative number, or a value that is not a number is a client error. The API answers **`400 Bad Request`**, not `500`:

```bash
curl -i "https://acme.orgo.space/api/v1/countries?page=0"
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"detail":"Page should not be less than 1","title":"Bad Request","status":400}
```

A `page` beyond the last page is not an error: you get an empty collection. Stop iterating when the collection is empty (or `hydra:next` is absent), not when you see an error.

### `pagination=false`

Clients cannot switch pagination off in general. The cap exists so one request cannot pull a whole tenant's data, so `?pagination=false` is ignored on almost every collection. The few collections that opt in advertise a `pagination` parameter in the reference (events and units, for example). On everything else, paginate.

## Iterating every page

The reliable way to iterate depends on which response format you accept.

### With JSON-LD (the default)

Follow `hydra:view.hydra:next` until it is absent:

```python
import requests

url = "https://acme.orgo.space/api/v1/users?itemsPerPage=100"
headers = {"Api-Token": "..."}

while url:
    resp = requests.get(url, headers=headers).json()
    for user in resp["hydra:member"]:
        process(user)
    url = resp.get("hydra:view", {}).get("hydra:next")
    if url and not url.startswith("http"):
        # Hydra returns relative URLs; join against the host
        url = f"https://acme.orgo.space{url}"
```

### With plain JSON

You get no totals or next-page links. Increment `page` until the response is shorter than `itemsPerPage`:

```python
page = 1
per_page = 100
while True:
    resp = requests.get(
        f"https://acme.orgo.space/api/v1/users?page={page}&itemsPerPage={per_page}",
        headers={"Api-Token": "...", "Accept": "application/json"}
    ).json()
    for user in resp:
        process(user)
    if len(resp) < per_page:
        break
    page += 1
```

<Tip>
For long-running exports, prefer JSON-LD. `hydra:totalItems` lets you display progress, and `hydra:next` is a stable signal that the server still has more rows.
</Tip>

## Filtering

Filters are query-string parameters. The available filters differ per resource. Unknown parameters are ignored rather than rejected, so a misspelled filter returns the unfiltered collection. Check that the result shrank.

### Exact-value filter

```bash
GET /api/v1/users?status=ACTIVE
GET /api/v1/events?status=published
```

User statuses are uppercase (`ACTIVE`). Several other statuses, such as event, payment, invoice, contract and vote statuses, are lowercase. Read the enum in the reference rather than guessing.

### Filter by relation

For most relations, pass the related resource's IRI:

```bash
GET /api/v1/event_attends?event=/api/v1/events/01938d8e-9c4f-7c2a-b8e1-3f7a9b8c4f12
GET /api/v1/contract_users?contract=/api/v1/contracts/9
```

Local centers are the exception on the people-related collections (users, contacts, adhesions, fee and product payments, roles). Their `localCenter` filter takes the **numeric id**, one value at a time, and answers `400 No Local Center with this id` for an id that does not exist or is out of reach:

```bash
GET /api/v1/users?localCenter=4
```

### Multi-value (OR)

Where a filter advertises the `name[]` form in the reference, repeat the parameter to match any of several values:

```bash
GET /api/v1/users?status[]=ACTIVE&status[]=INACTIVE
```

### Keyword search

User and event-like collections that support it take a `keyword` parameter. Check the endpoint for it, because the name differs on some resources (contacts use `search`, events use `name`):

```bash
GET /api/v1/users?keyword=patterson
GET /api/v1/events?name=annual+meeting
GET /api/v1/contacts?search=olivia
```

### Date range

Date filters use the `[before]`, `[after]`, `[strictly_before]`, `[strictly_after]` modifiers on the date properties each resource names:

```bash
GET /api/v1/events?dateTimeBegin[after]=2026-01-01T00:00:00Z
GET /api/v1/product_payments?stripePaymentDate[after]=2026-01-01&stripePaymentDate[before]=2026-12-31
GET /api/v1/users?dateJoined[after]=2025-01-01
```

### Presence

`exists[property]=true|false` tests whether a nullable property is set:

```bash
GET /api/v1/users?exists[isFullMember]=true
GET /api/v1/events?exists[unit]=false
```

### Custom-field filters

User collections accept `customFieldValues.field` (the custom field) and `customFieldValues.value` (the stored value), which narrow to members who hold that value for that field:

```bash
GET /api/v1/users?customFieldValues.field=/api/v1/custom_fields/8&customFieldValues.value=Vegetarian
```

## Ordering

Use `order[field]=asc|desc`. Order by several fields by repeating the parameter. Only the fields listed under the endpoint's parameters can be ordered:

```bash
# Single field, descending
GET /api/v1/events?order[dateTimeBegin]=desc

# Two fields: first by name, then by start date
GET /api/v1/events?order[name]=asc&order[dateTimeBegin]=desc

# By a related resource's field
GET /api/v1/users?order[localCenter.name]=asc&order[lastName]=asc
```

The default order varies per resource (usually newest first for "feed" resources like events and newsletters, alphabetic for reference data).

---

## Combining filters, ordering, and pagination

Stack them with `&`:

```bash
GET /api/v1/users?status=ACTIVE
              &localCenter=4
              &keyword=james
              &order[lastName]=asc
              &page=1
              &itemsPerPage=50
```

URL-encode parameter values that contain spaces or special characters (`?name=annual%20meeting`). Most HTTP clients do this for you.

---

## Performance notes

- Collection endpoints fetch and serialize each row's full read group. For large datasets, apply narrow filters first (`?status=ACTIVE` shrinks the row count before anything else happens).
- `itemsPerPage=100` is the maximum, so use it for exports to keep the request count low.
- Sorting by a non-indexed column on a large collection can be slow. Stick to the `order[...]` fields the reference lists.
