This walkthrough implements a production-grade webhook receiver for Orgo events. It covers subscription, idempotent handling, fast responses, and replay.

Who is this for: any integration that needs to react to changes in Orgo in near-real-time (CRM sync, member onboarding automation, payment reconciliation, contract-signed notifications).

---

## Available events

Twenty-four event types, across eight entity families. Subscribe to any subset.

| Family | Events |
|---|---|
| **User** | `user.created`, `user.updated`, `user.deleted` |
| **Payment** | `product_payment.created`, `product_payment.updated`, `product_payment.deleted` |
| **Event attendance** | `event_attend.created`, `event_attend.updated`, `event_attend.deleted` |
| **Contract** | `contract_user.created`, `contract_user.updated`, `contract_user.deleted` |
| **Role** | `user_role.created`, `user_role.updated`, `user_role.deleted` |
| **Contact** | `contact.created`, `contact.updated`, `contact.deleted` |
| **Badge** | `badge_user.created`, `badge_user.updated`, `badge_user.deleted` |
| **Badge step** | `badge_user_step.created`, `badge_user_step.updated`, `badge_user_step.deleted` |

## Step 1: Subscribe

Pick the events you care about and a public HTTP(S) endpoint you control (HTTPS in production). You need to be an Orgo administrator.

```bash
curl -X POST https://acme.orgo.space/api/v1/webhook_subscriptions \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CRM sync",
    "url": "https://your-app.example.com/webhooks/orgo",
    "eventTypes": [
      "user.created",
      "product_payment.created",
      "product_payment.updated"
    ],
    "secret": "whsec_a3f8b2c4d6e8f1a3b5c7d9e1f3a5b7c9",
    "isActive": true,
    "description": "Sync members and payments into our CRM."
  }'
```

`name`, `url` and `eventTypes` are required. The `secret` is yours to choose: a 32-byte random string is standard. Orgo uses it to sign each delivery so you can verify the payload came from Orgo. The address must be a public one on port 80 or 443; private and loopback addresses are refused with `422`. See [Webhooks](/api-reference/concepts/webhooks#subscribing) for every field, including `maxRetries` and `timeoutSeconds`.

The response includes the subscription `id`. Store it; you need it for the test and delivery-log calls.

## Step 2: Receive the delivery

Each event is delivered as an HTTPS `POST` with a JSON body and these headers:

| Header | Purpose |
|---|---|
| `X-Webhook-Event` | The event type, e.g. `user.created` |
| `X-Webhook-Delivery` | Unique delivery ID. Log this to correlate with the delivery logs |
| `X-Webhook-Timestamp` | Unix timestamp of when the delivery was sent |
| `X-Webhook-Signature` | `t=<timestamp>,v1=<hex>`, verified in Step 3 |
| `User-Agent` | `OrgoWebhook/1.0` |

Body shape (Stripe-inspired):

```json
{
  "id": "wh_evt_67aa128c2f4a",
  "event": "user.created",
  "api_version": "2024-01",
  "created": 1735689600,
  "tenant_id": 1,
  "request": {
    "id": "req_8c2f4a67aa12"
  },
  "object": {
    "@id": "/api/v1/users/42",
    "id": 42,
    "firstName": "James",
    "lastName": "Patterson",
    "email": "james.patterson@example.com",
    "status": "ACTIVE"
  },
  "previous_attributes": null,
  "is_update": false,
  "entity_type": "user",
  "operation": "created"
}
```

For `*.updated` events, `previous_attributes` carries the diff: fields not mentioned didn't change. This is enough to detect specific transitions ("user just unsubscribed", "payment just succeeded") without comparing to a stored snapshot.

## Step 3: Verify the signature

Do this before you look at the body. Your endpoint is reachable by anyone, so whatever arrives is unauthenticated until the signature says otherwise. A subscription created without a `secret` sends no signature header, so always set one.

`X-Webhook-Signature` is `t=<unix seconds>,v1=<hex>`, where `v1` is `HMAC-SHA256(secret, "<t>." + raw request body)`. The `t` is the same value as `X-Webhook-Timestamp`, and it is inside the signed string, so a captured delivery cannot be re-stamped and replayed.

```python
import hashlib, hmac, time

TOLERANCE_SECONDS = 300

def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    if "t" not in parts or "v1" not in parts:
        return False

    if abs(time.time() - int(parts["t"])) > TOLERANCE_SECONDS:
        return False   # replayed, or your clock is wrong

    expected = hmac.new(
        secret.encode(),
        parts["t"].encode() + b"." + raw_body,
        hashlib.sha256,
    ).hexdigest()

    return hmac.compare_digest(expected, parts["v1"])


@app.post("/webhooks/orgo")
def receive():
    if not verify(request.get_data(), request.headers.get("X-Webhook-Signature", ""), SECRET):
        return "", 401
    ...
```

Three rules the code above is built around:

- **Hash the raw bytes.** `request.get_data()`, not `request.get_json()` re-serialized. Key order and whitespace differ after a round trip, and the MAC changes with them.
- **Compare in constant time.** `hmac.compare_digest`, `crypto.timingSafeEqual`, `hash_equals`, never `==`.
- **Do not deduplicate on the signature.** Retries are re-signed at send time, so the same delivery ID arrives with a different `v1`. Dedupe on the payload `id`, as in Step 4.

Returning `401` marks the delivery failed and Orgo retries it, which is what you want when the cause is a secret you have just rotated on one side only.

A JavaScript version of the same function is in the [webhooks concept page](/api-reference/concepts/webhooks#authenticating-the-sender).

<Warning>
This format shipped in August 2026, replacing a short non-keyed checksum. There is no compatibility header, so a receiver comparing the old value must move to the recipe above.
</Warning>

## Step 4: Be idempotent

Orgo may deliver the same event twice: retries after a slow response, or network races on at-least-once delivery. Your handler must be safe to call repeatedly with the same payload.

The simplest pattern: a `processed_deliveries` table keyed by `id` (the top-level event ID, e.g. `wh_evt_67aa128c2f4a`):

```python
def handle_event(payload: dict) -> None:
    delivery_id = payload["id"]
    with db.transaction():
        if db.processed_deliveries.exists(delivery_id):
            return  # already handled, no-op
        db.processed_deliveries.insert(delivery_id, processed_at=now())
        dispatch(payload)
```

Insert the row *inside the same transaction* as the side effect, so a crash mid-way doesn't leave the row inserted without the effect. If the effect is in a different system (CRM API call), insert the row only after the effect succeeds.

## Step 5: Respond fast

Orgo waits for a response for the subscription's `timeoutSeconds` (30 by default) before treating the delivery as failed. Long-running work (sending a follow-up email, querying a slow downstream API) should go into a background queue. The webhook handler's job is to acknowledge receipt and durably queue the work, not perform it.

```python
@app.post("/webhooks/orgo")
def receive():
    payload = request.get_json()
    queue.enqueue("process_orgo_event", payload)   # < 50ms
    return "", 200
```

Return any 2xx; Orgo doesn't care about the body.

## Step 6: Test before going live

The test endpoint queues one synthetic delivery to the subscription URL. It takes no body:

```bash
curl -X POST https://acme.orgo.space/api/v1/webhook_subscriptions/3/test \
  -H "Api-Token: $ORGO_API_TOKEN"
```

The answer is `{"success": true, "message": "Test webhook dispatched successfully", "delivery_id": "..."}`, and the delivery happens a moment later. Its event type is always `webhook.test`, and its `object` describes the subscription (`name`, `url`, `event_types`, `is_active`) instead of a member, so do not route it through your real handlers. It carries the same headers and signature as a production delivery, which makes it the right check for your signature code and your firewall.

## Step 7: Replay failed deliveries

Every delivery attempt, success or failure, is logged. To list the most recent ones (up to `limit`, default 100, maximum 500):

```bash
curl "https://acme.orgo.space/api/v1/webhook_subscriptions/3/delivery_logs?limit=200" \
  -H "Api-Token: $ORGO_API_TOKEN"
```

Each log carries the original payload, your response status and body, and the time taken, so you can re-process a failed delivery locally without waiting for Orgo to send it again.

## Retry behavior

| Trigger | Behavior |
|---|---|
| Receiver returns 2xx | Marked delivered, no retries |
| Receiver returns non-2xx | Retried with exponential backoff while attempts remain |
| Receiver takes longer than `timeoutSeconds` | Treated as failed; retried |
| Receiver TLS or connection error | Treated as failed; retried |
| Address no longer allowed | Logged as failed; never retried |
| Attempts exhausted | Appears as failed in the delivery logs |

`maxRetries` (default 3, maximum 10) is the maximum number of attempts per delivery. With the default, Orgo calls your endpoint at most three times, 20 and then 40 seconds apart; the delay keeps doubling up to 10 minutes if you raise it.

The subscription itself is *not* automatically deactivated on repeated failures. Your monitoring should watch the subscription's `failedDeliveries` counter and either pause it (`PATCH` with `isActive: false`) or page on-call.

## Common gotchas

<AccordionGroup>
  <Accordion title="Deliveries are arriving out of order">
    Orgo doesn't guarantee delivery order across event types. The `created` timestamp on each event lets you reconstruct order, so sort by `created` before processing if order matters. For per-resource ordering ("two updates to the same user"), use `previous_attributes` to detect skipped transitions.
  </Accordion>

  <Accordion title="The same event arrives for different tenants in my multi-tenant CRM">
    Always route by `tenant_id` in the payload, not by the subscription ID. If a single CRM serves multiple Orgo tenants, each tenant should create its own subscription, and your receiver should route incoming events to the right CRM tenant based on `payload['tenant_id']`.
  </Accordion>

  <Accordion title="Can I subscribe to all events with a wildcard?">
    Not currently. List explicit event types in the `eventTypes` array; the full list is in the [Webhooks concept page](/api-reference/concepts/webhooks). A subscription will not pick up new types Orgo adds later, so patch it when new events ship.
  </Accordion>
</AccordionGroup>
