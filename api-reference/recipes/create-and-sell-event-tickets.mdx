title: 'Create and sell event tickets'
description: 'From draft event to ticket types, publication and registrations, with Stripe handling the payments'
---

This walkthrough creates a ticketed event, adds ticket types to it, publishes it, and registers attendees. The chain covers the [Event](/api-reference/event), [ProductPrice](/api-reference/productprice) and [EventAttend](/api-reference/eventattend) resources. Buyers pay through the public checkout described in [Build a public event landing page](/api-reference/recipes/build-a-public-event-landing-page).

Who is this for: integrations that need to provision events programmatically (recurring training, partner-organized meetups, automated festival setup) or surface Orgo's ticketing in a custom site.

---

## Prerequisites

- Stripe connected for the organization or the event's local center, see [Stripe integration](/platform/fees/stripe-integration). Without it, free tickets still work.
- An Api-Token from a user who may create events and enable ticketing (an administrator, or someone with organization-wide event rights) and create prices (organization-wide or chapter finance rights). Without those rights, `hasEventTicketing` is quietly turned off on creation, or the price call answers `403`.

---

## Step 1: Create the event as a draft

New events are always created as drafts, invisible to members and the public. You can edit freely until you publish. You do not send a `status`; the server sets it.

```bash
curl -X POST https://acme.orgo.space/api/v1/events \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Annual General Meeting 2026",
    "description": "Quarterly chapter meeting with working-group breakouts and a board Q&A.",
    "dateTimeBegin": "2026-03-15T18:00:00+00:00",
    "dateTimeEnd": "2026-03-15T21:00:00+00:00",
    "timezone": "America/New_York",
    "location": "Boston Public Library, 700 Boylston St, Boston, MA 02116",
    "unit": "/api/v1/units/4",
    "isPublic": true,
    "maxCapacity": 200,
    "hasEventTicketing": true,
    "requiresRegistrationForm": true
  }'
```

The response carries an integer `id` and a `uuid`. Events are addressed by `uuid` in their paths (`/api/v1/events/{uuid}`), so keep it. Setting `hasEventTicketing: true` creates the event's ticketing product for you; the response shows it in `product`.

```json
{
  "id": 12,
  "uuid": "01938d8e-9c4f-7c2a-b8e1-3f7a9b8c4f12",
  "name": "Annual General Meeting 2026",
  "status": "draft",
  "hasEventTicketing": true,
  "product": "/api/v1/products/01938d8e-c2f4-7c2a-b8e1-3f7a9b8c4f99"
}
```

Event statuses are lowercase (`draft`, `published`). If the dates are already in the past the event is created as `published`. A public event inside a group that is not joinable is forced to private.

## Step 2: Add ticket types

A ticket type in Orgo is a **price** on the event's product, not a product of its own. One event, one product, one `ProductPrice` per ticket type (general admission, member, early bird).

```bash
curl -X POST https://acme.orgo.space/api/v1/product_prices \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "product": "/api/v1/products/01938d8e-c2f4-7c2a-b8e1-3f7a9b8c4f99",
    "name": "General Admission",
    "price": 25.00,
    "currency": "USD",
    "isOneTime": true,
    "maxSeats": 120,
    "sortOrder": 1,
    "validFrom": "2026-01-15T00:00:00+00:00",
    "validTo": "2026-03-14T23:59:00+00:00"
  }'
```

`price` is in **currency units** (`25.00` is twenty-five dollars), not cents. A `price` of `0` makes a free ticket. `maxSeats` caps how many of this ticket can be sold; leave it out for no cap beyond the event's `maxCapacity`. The optional sales window (`validFrom`, `validTo`) cannot start before the event was created or end after the event ends, otherwise the call answers `400`. When a Stripe account is connected, the price is synced to Stripe.

Other useful fields: `groupName` (to group tickets on the page), `isRestricted` and `allowedFeeProductPrices` (members-only tickets), `ageUnder` and `ageOver`, `isHidden`. Repeat the call for each ticket type; the response returns the price `id` that buyers reference in checkout.

<Tip>
To retire a ticket type, set `isArchived: true` with `PATCH /api/v1/product_prices/{id}`. Archived tickets are no longer offered at checkout.
</Tip>

## Step 3: Publish the event

Publishing flips the event from `draft` to `published`, creates a notification and, for future events, tells the unit's members. It fails if the event is already published.

```bash
curl -X PATCH https://acme.orgo.space/api/v1/events_publish/01938d8e-9c4f-7c2a-b8e1-3f7a9b8c4f12 \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/merge-patch+json" \
  -d '{}'
```

After publishing, anyone can read the event with `GET /api/v1/get_public_event_anonymous/{uuid}` and the public registration page lives at `https://acme.orgo.space/public/event/{uuid}`. Before you publish, organizers can preview the page with a draft preview link (`PATCH /api/v1/events/{uuid}/preview-token`) and see ticket availability with `GET /api/v1/events/{uuid}/draft-availability`.

<Tip>
`/api/v1/event-go-publish/{uuid}` is the publish call used by the "Go" landing-page editor. Use `events_publish` from server-to-server integrations.
</Tip>

## Step 4: Register attendees

Buyers register and pay through the public checkout. For people you register yourself, there are two paths.

### Path A: an existing member

```bash
curl -X POST https://acme.orgo.space/api/v1/event_attends \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "event": "/api/v1/events/01938d8e-9c4f-7c2a-b8e1-3f7a9b8c4f12",
    "user": "/api/v1/users/42",
    "statusRsvp": "attending"
  }'
```

When the target user is not the caller, the registration is an **invitation**: the member gets an email, and for events with a registration form their answer is awaited. The response carries the attendance `id`, `statusRsvp`, `statusRegistration` (`invited` or `success`) and a `hash` that doubles as the QR check-in code. Duplicates are refused, and non-ticketed events respect `maxCapacity`.

### Path B: a person with no account

Invite them by email. Orgo matches the address against members first, then contacts, and creates a contact if neither exists:

```bash
curl -X POST https://acme.orgo.space/api/v1/event_attend_invite_external \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "entity": {
      "event": "01938d8e-9c4f-7c2a-b8e1-3f7a9b8c4f12",
      "email": "olivia.brown@example.com"
    },
    "skipEmail": false
  }'
```

Note that `event` here is the event's **uuid**, not an IRI, and the fields sit inside `entity`. The recipient receives a link they can open without an account. With `skipEmail: true` no email is sent and you register them on their behalf, then confirm them (below).

### Confirming an invited attendee

For VIP, speaker or complimentary access, confirm the invitation yourself. This upgrades the attendee to `success` and emails them a ticket with a QR code:

```bash
curl -X POST https://acme.orgo.space/api/v1/event_attends/1042/confirm \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Step 5: Payments

For paid tickets the buyer pays on the public checkout, where Stripe collects the card and Orgo records a `ProductPayment`. You never create the charge yourself. When the payment clears, the attendance becomes `success` and a ticket is emailed. React to it with the `product_payment.updated` and `event_attend.created` webhooks, see [Handle webhooks](/api-reference/recipes/handle-webhooks). Refunding a payment cancels the linked registration and returns the seat to the pool, see [Process payments](/api-reference/recipes/process-payments).

## Check-in on the day

At the venue, scan the attendee's QR code in the Orgo event app, or mark them attended through the API:

```bash
curl -X PATCH https://acme.orgo.space/api/v1/event_attends/1042 \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/merge-patch+json" \
  -d '{"statusRsvp": "attended"}'
```

RSVP states are `attending`, `maybe`, `not_attending` and `attended`. Setting `statusRegistration` to `success` by hand checks that payment is complete and the required form fields are filled, unless the caller manages the event.

## Common gotchas

<AccordionGroup>
  <Accordion title="My event published but the public page is not found">
    The public page only exists for events that are `published` and `isPublic: true`. Members-only events have no public page at all.
  </Accordion>

  <Accordion title="Ticketing was turned off on my new event">
    `hasEventTicketing` is only honored for callers with organization-wide event or finance rights. For anyone else the event is created without ticketing, with no error. Check the flag in the response.
  </Accordion>

  <Accordion title="The checkout fails with 'Stripe is not configured for this organization'">
    Paid tickets need a connected Stripe account for the organization or the event's local center, see [Stripe integration](/platform/fees/stripe-integration).
  </Accordion>

  <Accordion title="How do I sell free tickets that still require registration?">
    Set `hasEventTicketing: true` and `requiresRegistrationForm: true`, and create a ticket price with `price: 0`. Payment is skipped for a zero total, and the buyer completes with `complete-free` on the public checkout.
  </Accordion>

  <Accordion title="Can attendees bring guests?">
    Yes. After the main attendee is confirmed (`statusRegistration: success`), call `POST /api/v1/event_attends/{id}/guest-tickets` with `{"quantity": 3}`. A request takes 1 to 20 guests, and each guest ticket is generated as a PDF and emailed.
  </Accordion>
</AccordionGroup>
