This walkthrough sets up a two-way sync between an external CRM (HubSpot, Salesforce, Attio, or a homegrown one) and Orgo's `Contact` resource. The pattern: push contacts on a schedule, then keep both sides current incrementally through webhooks.

Who is this for: marketing-ops integrations that own the CRM and need to project contact data into Orgo so it can drive newsletters, event invites and audience filters.

Your Api-Token must belong to a user who can manage contacts (HR or finance rights over the contact's chapter). Tagging and newsletter subscription need organization-wide HR rights, and creating tags needs organization-wide admin rights.

---

## Architecture in two paragraphs

Your CRM is the source of truth for *contact details*. Orgo is the source of truth for *what that contact has done* inside Orgo: events attended, payments made, contracts signed, newsletter engagement. The sync pushes contact details one way and pulls Orgo activity the other way.

Both sides change day to day. Without webhooks you would poll Orgo for "what changed since yesterday", which is slow, and contacts have no "updated since" filter to poll with. With webhooks, Orgo tells you the moment a contact is created, edited or removed. Use webhooks for the Orgo to CRM direction.

## Step 1: Bulk import from the CRM to Orgo

Create one contact per CRM record with `POST /api/v1/contacts`. If the email already belongs to a contact **or a member**, the call answers `409 Conflict`, so you can rerun an import safely.

```bash
curl -X POST https://acme.orgo.space/api/v1/contacts \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "firstName": "Olivia",
    "lastName": "Brown",
    "email": "olivia.brown@example.com",
    "phone": "+1 415 555 0192",
    "organisation": "Brown & Co",
    "localCenter": "/api/v1/local_centers/4"
  }'
```

Contacts take `name` or `firstName` and `lastName`, plus `email`, `phone`, `organisation`, `role`, `town`, `country`, `gender`, `dateBirth`, social links, company fields, `customFieldValues` and `localCenter`. The response carries the contact `id`, `source: "MANUAL"` and the read-only `isNewsletterSubscribed` flag. Newsletter opt-in cannot be set on create, see step 3.

For thousands of contacts, parallelize with a modest cap (around 10 concurrent requests) rather than flooding the endpoint.

### Conflict handling

When `POST` returns `409`, the email already exists. Either skip it (your CRM was already in sync) or merge: look the contact up by email and update it with the fresher CRM data.

```bash
# Find the existing contact
curl "https://acme.orgo.space/api/v1/contacts?email=olivia.brown@example.com" \
  -H "Api-Token: $ORGO_API_TOKEN"

# Merge CRM updates into it
curl -X PATCH https://acme.orgo.space/api/v1/contacts/85 \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/merge-patch+json" \
  -d '{
    "phone": "+1 415 555 0199",
    "role": "Board member"
  }'
```

If the `409` is because the address belongs to a **member**, the email is not a contact at all: update the user instead, or leave it.

## Step 2: Tag contacts for audience filtering

Tags label contacts for filtering and for newsletter audiences. Mirror your CRM segments as tags. A tag is created once, then attached to each contact with a profile tag:

```bash
# Create the tag (organization-wide admin rights)
curl -X POST https://acme.orgo.space/api/v1/tags \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "donor-2026"}'
# -> {"id": 14, "name": "donor-2026", ...}

# Attach the tag to a contact (organization-wide HR)
curl -X POST https://acme.orgo.space/api/v1/profile_tags \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"tag": "/api/v1/tags/14", "contact": "/api/v1/contacts/85"}'
```

List a contact's tags with `GET /api/v1/contacts/85/profile_tags`, and find every contact with a tag using `GET /api/v1/contacts?tags.tag=/api/v1/tags/14`. Remove a tag from a contact by deleting the profile tag: `DELETE /api/v1/profile_tags/{id}`.

Run tagging after the initial import. One round trip per contact-tag pair is fine up to around ten thousand contacts.

### Newsletter subscription

Whether a contact receives newsletters is a flag Orgo manages, with an audit entry for every change. Set it with:

```bash
curl https://acme.orgo.space/api/v1/contact/85/subscribe-to-newsletter \
  -H "Api-Token: $ORGO_API_TOKEN"
# and .../unsubscribe-from-newsletter to turn it off
```

Both are `GET` calls and need organization-wide HR rights. Respect opt-outs: a person who unsubscribes through an email link has the flag turned off, and your sync should not turn it back on without their consent.

## Step 3: Subscribe to Orgo events

Register a webhook so Orgo pushes updates as they happen:

```bash
curl -X POST https://acme.orgo.space/api/v1/webhook_subscriptions \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CRM sync",
    "url": "https://your-app.example.com/webhooks/orgo",
    "eventTypes": [
      "contact.created",
      "contact.updated",
      "contact.deleted",
      "user.created",
      "user.updated",
      "product_payment.created"
    ],
    "secret": "whsec_a3f8b2c4d6e8f1a3b5c7d9e1f3a5b7c9",
    "isActive": true,
    "description": "Sync contact and member changes into CRM"
  }'
```

Creating webhook subscriptions needs the Orgo administrator flag. See [Handle webhooks](/api-reference/recipes/handle-webhooks) for the receiver implementation.

## Step 4: Receive and write back to the CRM

When Orgo fires a `contact.updated` webhook, your handler:

1. Verifies the signature.
2. Looks up the same contact in your CRM by email.
3. Writes back the fields Orgo owns (newsletter opt-in, attendance, payments).

The payload shape:

```json
{
  "id": "wh_evt_67aa128c2f4a",
  "event": "contact.updated",
  "tenant_id": 1,
  "created": 1735689600,
  "object": {
    "@id": "/api/v1/contacts/85",
    "id": 85,
    "name": "Olivia Brown",
    "email": "olivia.brown@example.com",
    "isNewsletterSubscribed": false
  },
  "previous_attributes": {
    "isNewsletterSubscribed": true
  }
}
```

`previous_attributes` is the diff: fields not mentioned did not change. That is enough to detect an unsubscribe without comparing against a stored snapshot.

## Step 5: Catch up after downtime

If your receiver was down, look at the subscription's recent delivery attempts:

```bash
curl "https://acme.orgo.space/api/v1/webhook_subscriptions/3/delivery_logs?limit=500" \
  -H "Api-Token: $ORGO_API_TOKEN"
```

The log lists successes and failures, with the payload of each attempt, up to 500 at a time. For each failed delivery, re-process the payload locally. Failed deliveries are retried automatically a few times (see [Webhooks](/api-reference/concepts/webhooks#retry-behavior)), so most short outages heal themselves.

For a longer outage, or if you suspect you missed events, run a reconciliation pass. Contacts cannot be filtered by update time, so page through the whole collection in a stable order and compare it with your CRM:

```bash
curl "https://acme.orgo.space/api/v1/contacts?order[id]=asc&itemsPerPage=100&page=1" \
  -H "Api-Token: $ORGO_API_TOKEN" \
  -H "Accept: application/json"
```

To pick up only new contacts since your last pass, order by creation: `order[dateCreated]=desc`, and stop when you reach a contact you already have.

## Common gotchas

<AccordionGroup>
  <Accordion title="My import is creating duplicate contacts">
    Orgo deduplicates by exact email, and only when a contact has an email. If your CRM holds several records for one person under different addresses, Orgo stores them as separate contacts. Dedupe in your CRM first, or merge in Orgo before syncing (see the merge tool under **Settings → Developers → Merge Records**).
  </Accordion>

  <Accordion title="A contact became a member mid-sync and my CRM has stale state">
    When a person becomes a member, a `user.created` webhook fires. Match it to your CRM record by email and point the record at the member. Do not assume the contact record disappears or stays; treat the email as the join key.
  </Accordion>

  <Accordion title="Webhook deliveries are failing silently">
    Check `GET /api/v1/webhook_subscriptions/3/delivery_logs`. Common causes: the receiver returns a non-2xx status, it takes longer than the subscription's `timeoutSeconds` (30 by default), a TLS problem, or an address Orgo refuses to call (private or non-standard port). Orgo makes up to `maxRetries` attempts (3 by default) before giving up.
  </Accordion>

  <Accordion title="Can I import members directly instead of contacts?">
    Only HR with organization-wide rights can create members, with `POST /api/v1/member-register-by-admin`, which sends each person a welcome email. For most CRM use cases contacts are the right primitive: promote selected ones to members through the application flow when they are ready, see [Onboard a new member](/api-reference/recipes/onboard-a-new-member).
  </Accordion>
</AccordionGroup>
